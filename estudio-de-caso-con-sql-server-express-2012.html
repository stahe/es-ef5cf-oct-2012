    3. Estudio de caso con SQL Server Express 2012

    3.1. Introducción

    La mayoría de los ejemplos que se encuentran en línea sobre Entity Framework son ejemplos que utilizan SQL Server. Esto es bastante normal. Probablemente sea el SGBD más utilizado en el mundo empresarial de .NET. Seguiremos esta tendencia. Los ejemplos se ampliarán posteriormente a todas las bases de datos mencionadas en la sección 1.2.

    Contiene información sobre los médicos gestionados por la aplicación [RdvMedecins].

    Sin salir de la carpeta [Models], creamos el siguiente archivo [Context.cs]:

    
using System.Data.Entity;
using RdvMedecins.Entites;
 
namespace RdvMedecins.Models
{
 
  // the context
  public class RdvMedecinsContext : DbContext
  {
    // the doctors
    public DbSet<Medecin> Medecins { get; set; }
  }
 
  // database initialization
  public class RdvMedecinsInitializer : DropCreateDatabaseAlways<RdvMedecinsContext>
  {
  }
}
    • línea 8: la clase [RdvMedecinsContext] representará el contexto de persistencia, es decir, el conjunto de entidades gestionadas por el ORM. Debe derivar de la clase [System.Data.Entity.DbContext];
    • línea 11: el campo [Medecins] representa las entidades [Medecin] en el contexto de persistencia. Es de tipo DbSet<Medecin>. Por lo general, hay tantos [DbSet]s como tablas hay en la base de datos, uno por tabla;
    • línea 15: definimos una clase [RdvMedecinsInitializer] para inicializar la base de datos creada. Aquí, deriva de la clase [DropCreateDataBaseAlways], que, como su nombre indica, elimina la base de datos si ya existe y luego la vuelve a crear. Esto resulta útil durante la fase de desarrollo de la base de datos. El parámetro de la clase [DropCreateDataBaseAlways] es el tipo de contexto de persistencia asociado a la base de datos. Para la clase de inicialización se pueden utilizar otras clases padre además de [DropCreateDataBaseAlways]:
    • [DropCreateDatabaseIfModelChanges]: vuelve a crear la base de datos si las entidades han cambiado,
    • [CreateDatabaseIfNotExists]: crea la base de datos si no existe;

using System;
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;
 
namespace RdvMedecins.Entites
{
  [Table("MEDECINS", Schema = "dbo")]
  public class Medecin
  {
    // data
    [Key]
    [Column("ID")]
    public int Id { get; set; }
    [Required]
    [MaxLength(5)]
    [Column("TITRE")]
    public string Titre { get; set; }
    [Required]
    [MaxLength(30)]
    [Column("NOM")]
    public string Nom { get; set; }
    [Required]
    [MaxLength(30)]
    [Column("PRENOM")]
    public string Prenom { get; set; }
    [Required]
    [Column("VERSION")]
    public int Version { get; set; }
  }
}
    • Líneas 2 y 3: Las anotaciones se encuentran en el espacio de nombres [System.ComponentModel.DataAnnotations] (Key, Required, MaxLength) y en el espacio de nombres [System.ComponentModel.DataAnnotations.Schema] (Column). Se pueden encontrar anotaciones adicionales en la URL [http://msdn.microsoft.com/en-us/data/gg193958.aspx];
    • línea 11: [Key] designa la clave principal;
    • línea 12: [Column] establece el nombre de la columna correspondiente al campo;
    • línea 14: [Required] indica que el campo es obligatorio (SQL NOT NULL);
    • línea 15: [MaxLength] establece la longitud máxima de la cadena, [MinLength] su longitud mínima;

    • las columnas tienen los nombres que les hemos asignado;
    • la anotación [Required] se ha traducido a SQL NOT NULL;
    • La anotación [MaxLength(N)] se ha asignado al tipo SQL nvarchar(N).

    En la aplicación NHibernate, la columna [VERSION] estaba ahí para evitar el acceso simultáneo a la misma fila de una tabla. El principio es el siguiente:

    • Un proceso P1 lee una fila L de la tabla [DOCTORS] en el momento T1. La fila tiene la versión V1;
    • Un proceso P2 lee la misma fila L de la tabla [DOCTORS] en el momento T2. La fila tiene la versión V1 porque el proceso P1 aún no ha confirmado su modificación;
    • El proceso P1 confirma su modificación en la fila L. La versión de la fila L cambia entonces a V2 = V1 + 1;
    • El proceso P2 confirma su modificación en la fila L. A continuación, el ORM lanza una excepción porque el proceso P2 tiene una versión V1 de la fila L que difiere de la versión V2 que se encuentra en la base de datos.

    Esto se denomina gestión optimista de la concurrencia. Con EF 5, un campo que desempeñe esta función debe tener uno de estos dos atributos: [Timestamp] o [ConcurrencyCheck]. SQL Server dispone de un tipo [timestamp]. SQL Server genera automáticamente el valor de una columna de este tipo cada vez que se inserta o modifica una fila. Dicha columna puede utilizarse entonces para gestionar el acceso concurrente. Volviendo al ejemplo anterior, el proceso P2 encontrará una marca de tiempo diferente a la que leyó, ya que, entretanto, la modificación realizada por el proceso P1 la habrá cambiado.

    3.4.2. La entidad [Creneau]

    La tabla [CRENEAUX] enumera los intervalos de tiempo en los que es posible concertar citas:

    • ID: el número de identificación del intervalo de tiempo; la clave principal de la tabla
    • VERSION: número que identifica la versión de la fila en la tabla. Este número se incrementa en 1 cada vez que se realiza un cambio en la fila.
    • ID_MEDECIN: número de identificación del médico al que pertenece este horario – clave externa en la columna MEDECINS(ID).
    • START_TIME: hora de inicio de la franja horaria
    • MSTART: Minuto de inicio de la franja horaria
    • HFIN: hora de finalización de la franja horaria
    • MFIN: minutos de finalización de la franja

    La segunda fila de la tabla [SLOTS] (véase [1] más arriba) indica, por ejemplo, que la franja n.º 2 comienza a las 8:20 a. m. y termina a las 8:40 a. m., y que pertenece a la doctora n.º 1 (Sra. Marie PELISSIER).

    Con lo que sabemos, podemos definir la entidad [Creneau] de la siguiente manera en [Entites.cs]:

    
[Table("CRENEAUX", Schema = "dbo")]
  public class Creneau
  {
    // data

    [Column("ID")]
    public int? Id { get; set; }
    [Required]
    [Column("HDEBUT")]
    public int Hdebut { get; set; }
    [Required]
    [Column("MDEBUT")]
    public int Mdebut { get; set; }
    [Required]
    [Column("HFIN")]
    public int Hfin { get; set; }
    [Required]
    [Column("MFIN")]
    public int Mfin { get; set; }
    [Required]
    public virtual Medecin Medecin { get; set; }
    [Column("TIMESTAMP")]
    [Timestamp]
    public byte[] Timestamp { get; set; }

El nombre del campo es irrelevante; solo importa el tipo. La propiedad debe declararse virtual utilizando la palabra clave virtual. Esto se debe a que EF necesita redefinir todas las denominadas propiedades de navegación, es decir, aquellas que corresponden a una clave externa y permiten la navegación entre tablas.

    3.5.1. Eliminación de elementos del contexto de persistencia

    Tenemos una base de datos con datos. Vamos a vaciarla. Creamos una nueva clase [Erase.cs] en el proyecto actual [1]:

using RdvMedecins.Models;

{
  class Erase
  {
    static void Main(string[] args)
    {

using System;
using System.Data;
using System.Linq;
using RdvMedecins.Entites;
using RdvMedecins.Models;
 
namespace RdvMedecins_01

  class ModifyAttachedEntity
  {
    static void Main(string[] args)
    {
      Client client1, client2, client3;
      // 1st context
      using (var context = new RdvMedecinsContext())
      {
        // empty the current base
        foreach (var client in context.Clients)
        {
          context.Clients.Remove(client);
        }
        foreach (var medecin in context.Medecins)
        {
          context.Medecins.Remove(medecin);
        }
        // add a customer
        client1 = new Client { Nom = "xx", Prenom = "xx", Titre = "xx" };
        context.Clients.Add(client1);
        // follow-up
        Console.WriteLine("client1--avant");
        Console.WriteLine(client1);
        // save context
        context.SaveChanges();
        // follow-up
        Console.WriteLine("client1--après");
        Console.WriteLine(client1);
      }
      // 2nd context
      using (var context = new RdvMedecinsContext())
      {
        // retrieve client1 from client2
        client2 = context.Clients.Find(client1.Id);
        // follow-up
        Console.WriteLine("client2");
        Console.WriteLine(client2);
        // modify client2
        client2.Nom = "yy";
        // save context
        context.SaveChanges();
      }

      using (var context = new RdvMedecinsContext())

        client3 = context.Clients.Find(client2.Id);

    3.5.6. Gestión de entidades desacopladas

    Volvamos a la arquitectura por capas de una aplicación como la del caso práctico:

    La capa [DAO] utiliza el ORM de EF5 para acceder a los datos. Contamos con los componentes básicos de esta capa. Cada método abrirá un contexto de persistencia, realizará las operaciones necesarias (insertar, actualizar, eliminar, consultar) y, a continuación, lo cerrará.     • un proceso P1 lee una fila L de la tabla [DOCTORS] en el momento T1. La fila tiene la marca de tiempo TS1;

    • el proceso P1 confirma su modificación en la fila L. La marca de tiempo de la fila L cambia entonces a TS2;
    • El proceso P2 confirma su modificación en la fila L. A continuación, el ORM lanza una excepción porque el proceso P2 tiene una marca de tiempo TS1 para la fila L que difiere de la marca de tiempo TS2 que se encuentra en la base de datos.

    Esto se denomina gestión optimista de la concurrencia. Con EF 5, un campo que desempeñe esta función debe tener uno de estos dos atributos: [Timestamp] o [ConcurrencyCheck]. SQL Server tiene un tipo [timestamp]. El valor de una columna de este tipo es generado automáticamente por SQL Server al insertar o modificar una fila. Dicha columna puede utilizarse entonces para gestionar la concurrencia.
